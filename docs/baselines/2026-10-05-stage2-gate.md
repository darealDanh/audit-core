# Stage 2 gate procedure — tplink DL110 v2 1.0.11

**Status: NOT RUN.** See [§7](#7-this-gate-has-not-been-run) before citing
anything in this document as a result.

This file is the procedure, not a measurement. No baseline file is created by
writing it. When the gate is actually run, its two runs are recorded in a new
dated baseline document; this file is not edited in place.

## 1. The gate, verbatim

From the design spec, §7, Stage 2:

> **Stage 2 — Structural change.** Benchmark-gated. `audit_core` (db, extract,
> annotations, coverage, sweep, budget); R1; R3; vendored into `codebase-audit`
> with its existing phase semantics unchanged. Gate: tplink re-run twice — cost
> must fall and recall must be ≥ 9/19.

The spec's §5.3 target table reads `9` in the "CRITICALs vs. 19-item reference
set" row where an earlier draft read `8`. The figure is 9 because of the
REF-19 ~ G5-F1 adjudication of 2026-10-05, recorded in the golden's
`README.md` adjudication log and in `matches.json`. **Nine is the floor, not
the goal**: the §5.3 target for the whole programme is ≥ 12.

The rule that governs when the two halves of the gate disagree is §6.1:

> **Gate: no change merges if recall drops.** Cost targets are subordinate.

So a Stage 2 that halves cost and returns 8/19 does not merge. A Stage 2 that
returns 9/19 at unchanged cost has not passed either — but it has not failed
the *quality* test, and the correct response is to find the cost, not to
relax the recall floor.

## 2. What "cost must fall" is measured against

The comparison is against `docs/baselines/2026-10-05-tplink-baseline.md`, and
only against that file. `2026-10-04-tplink-baseline.md` is superseded and its
economics figures must not be cited.

| Metric | Baseline |
|---|---|
| Cost | $658.37 |
| Σ context | 224.2M (224,151,346) |
| Billed turns | 843 (of 857 API calls) |
| Mean context | 265,897 |
| Growth rate `g` | ~2,573 tok/turn (2,572.66) |
| Compaction epochs | 7 |
| Recall | 9/19 (47.4%) |
| Cost per matched finding | $73.15 |

Those figures come from a transcript pinned at **15,608,662 bytes**, sha256
`a33f2f5213961c3bac5e65a7d0d3fa0c8673703972f500d54608ea3e49dfa6ca`. `budget`
prints `source_bytes` and `source_sha256` on every run; if the pinned pair is
not what the baseline records, the comparison is against a different session
and the result is void.

The target the cost is moving *toward* is §5.3's `≤ $45`. Stage 2 is not
expected to reach it; it is expected to move.

## 3. Why two runs

§6.1's first acknowledged limitation:

> **Non-determinism.** A single run is a noisy measurement. Milestone gates
> require two runs, and a one-finding delta is treated as noise.

Both runs are recorded in full — cost, turns, Σ context, recall, candidates,
coverage — and **the gate is judged on the pair, not on the better one**.
Reporting the cheaper run, or the run with the higher recall, and omitting the
other is the specific failure this clause exists to prevent.

A one-finding recall delta between the two runs is noise. A delta that puts
either run below 9/19 is not: §6.1's merge rule is about the measurement, and
a run that scored 8 was a run that scored 8.

## 4. The commands

Run twice, into two separate run directories. `__SKILL_DIR__` is the installed
skill root (`~/.claude/skills/codebase-audit/`); in-repo, it is the repository
root.

### 4.1 Per run

```bash
# 1. MCP preflight, then the strict relaunch (R4).
python3 __SKILL_DIR__/audit.py preflight --server autorev=<command>
claude --strict-mcp-config --mcp-config .audit-mcp.json

# 2. Workspace + schema.
python3 __SKILL_DIR__/audit.py init --root ~/Documents/Offsec/Opswat/Devices/tplink

# 3. The phases, at their user gates, manually compacting at each boundary.
/codebase-audit recon
/codebase-audit deploy
/codebase-audit audit
/codebase-audit fpcheck
/codebase-audit verify <finding-ids>   # forked, one finding at a time
/codebase-audit report                 # runs inside each verify fork
```

`deploy` and `verify` need a live instance. If the gate is run source-only,
that must be stated with the result, because it changes what "recall" is
measuring — and a source-only pair is not comparable to the live baseline.

### 4.2 For the record, after each run

```bash
RUN=~/Documents/Offsec/Opswat/Devices/tplink/reports/audit-<timestamp>
SESSION=~/.claude/projects/-Users-danhnguyen-Documents-Offsec-Opswat-Devices-tplink/<id>.jsonl

python3 __SKILL_DIR__/audit.py budget --report "$SESSION" --project
python3 __SKILL_DIR__/audit.py bench \
  --golden tests/goldens/tplink-dl110v2-1.0.11 \
  --db "$RUN/audit.db" \
  --cost <measured cost>
python3 __SKILL_DIR__/audit.py coverage --db "$RUN/audit.db"
python3 __SKILL_DIR__/audit.py status --db "$RUN/audit.db"
```

`budget --project` is run rather than bare `budget` because the projection and
the linearity table are part of the record (§5 below).

`bench` prints any candidate pairs. Those are **proposals, not results**. A
candidate is adjudicated by a human against both sides in full, and then lands
in `matches.json` (accepted) or `rejections.json` (rejected, with a reason).
Neither file may be written by a scoring run, and a recall figure quoted
before outstanding candidates are adjudicated is provisional.

## 5. Deterministic leading indicators to record alongside

§6.1 names these as what to use *between* milestones, because they do not need
a second run to mean something. Record them for each of the two runs anyway:
they are the diagnosis when the gate's headline numbers disagree.

| Indicator | Source |
|---|---|
| Coverage percentage (analyzed ÷ inventoried) | `audit.py coverage --db <audit.db>` |
| `not_audited` row count, with reasons | `audit.py coverage --db <audit.db>` |
| Surfaces opened | `audit.py rows --db <audit.db> --table cba_attack_surface` |
| Sweep hit counts | `audit.py rows --db <audit.db> --table cba_pattern_hits` |
| Measured linearity deviation per epoch | `audit.py budget --report <session> --project` |

The linearity figure is the one that says whether the R3 ceiling model is
still describing the session. Against the pinned baseline transcript it is
clean — epoch 0: 1.2%, 1: 0.2%, 2: 0.8%, 3: 0.3%, 4: 4.6% (worst), 5: 0.6%,
6: 2.7%, all far under the 30% threshold at which `project()`'s
turns-to-checkpoint number stops being trustworthy. A Stage 2 run whose worst
deviation jumps into the tens of percent is reporting that R1's extract-and-
dispatch changed the *shape* of context growth, which is a finding about the
model regardless of what the cost line says.

## 6. If cost falls and recall falls with it

§5.3, on its target table's last row:

> The last row is the gate. If cost falls and recall falls with it, the design
> has failed.

**The stage does not merge.** The response is not to re-run until a pair comes
out favourable, and not to argue the delta is noise — §6.1 already allows for
noise, at one finding, and a drop below 9/19 across both runs is outside it.
The response is to attribute the loss. Stage 2's levers are independently
revertible by design (R1, R3, and the `audit_core` extraction are separate
commits), so the attribution question is answerable: revert the suspected
lever and re-run, rather than reverting the stage.

## 7. This gate has not been run

**Nothing in this repository constitutes a Stage 2 gate result.** The gate is
two full tplink audit runs; the unit suite is not a proxy for it, and a green
`pytest -q`, a clean `lint-skill` and a clean `selftest` say only that the
code does what its tests say. Stage 2's code may be complete, reviewed and
merged while this gate is still open — what must not happen is this gate being
*reported* as passed on the strength of the unit suite. Two standing
verification gaps carried from Stage 1 belong in the same list, so the open
items live in one place:

1. **The Stage 2 gate has not been run.** No tplink re-run has happened since
   the Stage 2 work began. The only recall figure this repository holds,
   9/19, is from the pre-Stage-2 pinned run of 2026-09-28.
2. **`install.ps1` has never been executed.** No PowerShell exists on the
   development machine; every change to it across Stage 0, Stage 1 and
   Stage 2 was verified by reading it against the bash logic. A Windows smoke
   test remains the single highest-value verification this project does not
   have.
3. **`preflight` output has never been handed to a client that connected a
   real MCP server.** `.audit-mcp.json` is verified at config-content level
   only. R4's whole value is that the strict relaunch still has the servers
   the run needs, and that end of it is untested — which also means §4.1's
   first two commands above are themselves unverified in practice.

Gap 3 is inside this procedure, not beside it: the first run of the gate is
also the first real test of R4. If the strict relaunch comes up without
`autorev`, stop and fix the config rather than continuing without it — a run
that silently lost its MCP server is not a measurement of Stage 2.
