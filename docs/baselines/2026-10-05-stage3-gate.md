# Stage 3 gate procedure — tplink DL110 v2 1.0.11

**Status: NOT RUN.** See [§7](#7-this-gate-has-not-been-run) before citing
anything in this document as a result.

This file is the procedure, not a measurement. No baseline file is created by
writing it. When the gate is actually run, its two runs are recorded in a new

## 1. The gate, verbatim

From the design spec, §7, Stage 3:

> **Stage 3 — Quality additions.** Each benchmarked separately so attribution
> is possible. Pivot rule, sweep-on-confirm, coverage denominator, identity
> discipline, chain composition. Then, last and alone, Sonnet tiering for
> `surface`, L-sink and `fpcheck` — the one tiering change that can cost
> quality, with precision measured before and after.

The tiering half of this gate is a separate, later procedure — it is not run
as part of the Stage 3 gate below, and its own document is
[`2026-10-05-stage3-tiering-gate.md`](2026-10-05-stage3-tiering-gate.md).
This document is the gate for the five mechanisms: the pivot rule,
sweep-on-confirm, the coverage denominator, identity discipline and chain
composition.

The floor those five mechanisms are held to is the same one Stage 2 was held
to, from §6.1:

> **Gate: no change merges if recall drops.** Cost targets are subordinate.

and the same numeric floor, from §7's Stage 2 entry: recall must be **≥ 9/19**.
Nothing in Stage 3's design raises that floor; it is carried forward because
no later stage has re-measured it upward yet (§7's target for the whole
programme is ≥ 12/19, at Stage 4).

**The Stage 2 gate is also still open.** No tplink re-run has happened since
Stage 2's work began — see
[`2026-10-05-stage2-gate.md`](2026-10-05-stage2-gate.md), whose own §7 says
so. That means **a Stage 3 benchmark run measures Stage 2 and Stage 3
together**, unless Stage 2 is gated first on its own pair of runs. This
document does not decide that sequencing. Whether to gate Stage 2 alone
before gating Stage 3, or to accept a combined-stage measurement and
attribute afterward by reverting commits, is the operator's call to make
before running anything below.

## 2. Separate benchmarking, and why it is expensive

§7 wants each of the five additions "benchmarked separately so attribution is
possible". A benchmark, per §6.1, is a full tplink audit run, and §6.1 also
requires two runs per gate to absorb non-determinism. Five additions, each
benchmarked separately with its own before/after pair, is **ten full tplink
audit runs**. At the pinned baseline of $658.37 per run
(`2026-10-05-tplink-baseline.md`), that is on the order of $6,500 to attribute
five mechanisms individually. Nobody is going to run that, and this document
does not pretend otherwise.

**The affordable alternative:** the five additions ship as five separate,
independently revertible commits (the same discipline Stage 2's gate document
already uses for R1/R3/the `audit_core` extraction, in its own §6). The gate
below runs **once** for the whole stage — one pair of tplink runs, all five
mechanisms active. If the pair clears the floor, the stage merges as a unit.
If recall drops, attribution comes from reverting one suspected commit and
re-running, not from having measured each addition's isolated effect up
front.

**This is weaker than what §7 asks for.** §7 asks for five attributed
measurements before merge; this procedure gives one combined measurement at
merge time and a revert-and-re-run path afterward, only if something goes
wrong. A mechanism that is individually harmful but whose effect is masked or
offset by another in the same combined run would not be caught unless recall
actually drops below the floor. That is the cost of affording one gate
instead of ten runs, and it is stated here rather than presented as
equivalent to separate attribution.

## 3. Deterministic leading indicators

§6.1 names these as what to use *between* milestones, because none of them
need a second run to mean something. They are also the reason this stage is
worth shipping before its gate runs at all: every one of them is non-zero
today, against an empty or silent baseline in Stage 2.

| Indicator | Command | What a Stage 3 run should show against Stage 2 |
|---|---|---|
| Coverage percentage and gate verdict | `audit.py coverage --db <db> --gate --phase audit` | a denominator exists at all; Stage 2 runs had none |
| `not_audited` rows with reasons | `audit.py coverage --db <db>` | non-zero, with reasons, rather than silence |
| Patterns registered and swept | `audit.py patterns --db <db>` | non-zero registered, zero unswept |
| Pattern sweep hits | `audit.py rows --db <db> --table cba_pattern_hits` | the sweep found call sites the per-group pass did not |
| Pivot observations | `audit.py rows --db <db> --table cba_security_observations` | one per FALSE_POSITIVE verdict |
| Components with evidence | `audit.py identify --db <db>` | one per confirmed artifact |
| Chain candidates and compositions | `audit.py chain --db <db>`; `audit.py rows --db <db> --table cba_chains` | proposals read; compositions recorded |
| Precision | `audit.py bench --golden <g> --db <db>` | a number, for the first time |

Record these for both runs of the pair; they are the diagnosis when the
gate's headline recall number does not move the way the mechanisms predict.

## 4. The commands

Run twice, into two separate run directories. `__SKILL_DIR__` is the installed
skill root (`~/.claude/skills/codebase-audit/`); in-repo, it is the repository
root. These are §4 of the Stage 2 gate document with the Stage 3 verbs added.

### 4.1 Per run

```bash
# 1. MCP preflight, then the strict relaunch (R4).
python3 __SKILL_DIR__/audit.py preflight --server autorev=<command>
claude --strict-mcp-config --mcp-config .audit-mcp.json

# 2. Workspace + schema.
python3 __SKILL_DIR__/audit.py init --root ~/Documents/Offsec/Opswat/Devices/tplink

# 3. The phases, at their user gates, manually compacting at each boundary.
/codebase-audit recon
/codebase-audit deploy
/codebase-audit audit
/codebase-audit fpcheck
/codebase-audit verify <finding-ids>   # forked, one finding at a time
/codebase-audit report                 # runs inside each verify fork
```

`deploy` and `verify` need a live instance. If the gate is run source-only,
that must be stated with the result, because it changes what "recall" is
measuring — and a source-only pair is not comparable to the live baseline.

### 4.2 For the record, after each run

**Two different roots are in play here.** `install.sh` copies `audit.py` and
`audit_core/` into the installed skill; it does **not** copy `tests/`. The
golden set therefore lives only in the repository checkout, and
`--golden tests/goldens/...` will not resolve against `__SKILL_DIR__`. Name
the two roots separately:

```bash
REPO=~/Documents/Offsec/Tools/codebase-audit     # holds tests/goldens/
RUN=~/Documents/Offsec/Opswat/Devices/tplink/reports/audit-<timestamp>
SESSION=~/.claude/projects/-Users-danhnguyen-Documents-Offsec-Opswat-Devices-tplink/<id>.jsonl

python3 __SKILL_DIR__/audit.py budget --report "$SESSION" --project

# bench is run from the checkout, because the golden ships only there.
python3 "$REPO/audit.py" bench \
  --golden "$REPO/tests/goldens/tplink-dl110v2-1.0.11" \
  --db "$RUN/audit.db" \
  --cost <measured cost>

# --phase is load-bearing and is the scope workflows/audit.md actually runs.
# Unscoped, a unit recon ruled on and the audit phase never opened still
# counts as analyzed, so the gate reports 100% and passes on exactly the
# failure it exists to catch (reproduced: 1/1 PASS unscoped, 0/1 FAIL with
# --phase audit). Record the unscoped number too if you want it, but the
# verdict that belongs in the gate record is the phase-scoped one.
python3 __SKILL_DIR__/audit.py coverage --db "$RUN/audit.db" --gate --phase audit
python3 __SKILL_DIR__/audit.py patterns --db "$RUN/audit.db"
python3 __SKILL_DIR__/audit.py identify --db "$RUN/audit.db"
python3 __SKILL_DIR__/audit.py chain --db "$RUN/audit.db"
python3 __SKILL_DIR__/audit.py rows --db "$RUN/audit.db" --table cba_pattern_hits
python3 __SKILL_DIR__/audit.py rows --db "$RUN/audit.db" --table cba_security_observations
python3 __SKILL_DIR__/audit.py rows --db "$RUN/audit.db" --table cba_chains
python3 __SKILL_DIR__/audit.py status --db "$RUN/audit.db"
```

If the checkout and the installed skill are at different commits, `bench` is
scoring with the checkout's scorer. For a gate run they must be the same
commit; check with `git -C "$REPO" rev-parse --short HEAD` and record it
beside the result.

`budget --project` is run rather than bare `budget` because the projection and
the linearity table are part of the record, exactly as the Stage 2 gate
document's §5 requires.

`bench` prints any candidate pairs. Those are **proposals, not results**. A
candidate is adjudicated by a human against both sides in full, and then lands
in `matches.json` (accepted) or `rejections.json` (rejected, with a reason).
Neither file may be written by a scoring run, and a recall figure quoted
before outstanding candidates are adjudicated is provisional.

## 5. If recall falls

§6.1's rule, verbatim:

> **Gate: no change merges if recall drops.** Cost targets are subordinate.

**The stage does not merge.** The response is not to re-run until a pair comes
out favourable, and not to argue the delta is noise — §6.1 already allows for
noise, at one finding, and a drop below 9/19 across both runs is outside it.
The response is to attribute the loss: each of the five mechanisms is its own
commit (§2 above), so the attribution path is to revert the suspected commit
and re-run, exactly as Stage 2's gate document specifies for Stage 2's own
levers (R1, R3, the `audit_core` extraction).

## 6. What this gate does not cover

This procedure gates the five mechanisms only. It does **not** gate the
Sonnet tiering change for feature mapping and `fpcheck` — that change is held,
not shipped, and its own procedure and before/after gate are in
[`2026-10-05-stage3-tiering-gate.md`](2026-10-05-stage3-tiering-gate.md). Do
not treat a clean run of this gate as license to apply that diff; the two are
measured separately because the tiering change can cost precision in a way
none of the five mechanisms are designed to.

## 7. This gate has not been run

**Nothing in this repository constitutes a Stage 3 gate result.** The gate is
two full tplink audit runs; the unit suite is not a proxy for it, and a green
`pytest -q`, a clean `lint-skill` and a clean `selftest` say only that the
code does what its tests say. Stage 3's code may be complete, reviewed and
merged while this gate is still open — what must not happen is this gate being
*reported* as passed on the strength of the unit suite. The standing
verification gaps carried from Stage 2, plus the one this stage adds, belong
in the same list so the open items live in one place:

1. **The Stage 2 gate has not been run.** No tplink re-run has happened since
   the Stage 2 work began. The only recall figure this repository holds,
   9/19, is from the pre-Stage-2 pinned run of 2026-09-28.
2. **`install.ps1` has never been executed.** No PowerShell exists on the
   development machine; every change to it across Stage 0 through Stage 3 was
   verified by reading it against the bash logic. A Windows smoke test
   remains the single highest-value verification this project does not have.
3. **`preflight` output has never been handed to a client that connected a
   real MCP server.** `.audit-mcp.json` is verified at config-content level
   only. R4's whole value is that the strict relaunch still has the servers
   the run needs, and that end of it is untested — which also means §4.1's
   first two commands above are themselves unverified in practice.
4. **No precision figure exists for any run on the current configuration.**
   `bench` can score precision as of Stage 3 Task 7, but the only precision
   figure this repository holds — 39/40 (97.5%), against the pinned
   pre-Stage-2 tplink run of 2026-09-28 — is not a measurement of this
   stage's configuration, and is not itself a tiering-gate baseline. See
   [`2026-10-05-stage3-tiering-gate.md`](2026-10-05-stage3-tiering-gate.md)
   for why, and for the precision-before/precision-after procedure that would
   close this gap.

Gap 3 is inside this procedure, not beside it: the first run of this gate is
also the first real test of R4. If the strict relaunch comes up without
`autorev`, stop and fix the config rather than continuing without it — a run
that silently lost its MCP server is not a measurement of Stage 3.
